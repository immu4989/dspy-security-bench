# v0.7.0 — ProofRun: evidence you can verify

v0.7.0 introduces a provenance layer for agent-security evaluation. ProofRun
combines RepeatTwin's raw stochastic trials and confidence bounds with a
portable, content-addressed bundle and GitHub/Sigstore provenance for the exact
evidence bytes.

## The new path

```yaml
permissions:
  contents: read
  id-token: write
  attestations: write

jobs:
  proofrun:
    uses: immu4989/dspy-security-bench/.github/workflows/proofrun.yml@v0.7.0
    with:
      agent: myapp.security:build_agent
      trials: 10
      min-lower-bound: 0.80
```

The reusable workflow checks out the evaluated commit, installs an immutable
v0.7.0 benchmark engine, executes every clean/poisoned pair with a fresh agent,
and preserves the bundle before enforcing the gate. It uses GitHub's OIDC and
artifact-attestation service to sign an in-toto provenance statement, then
uploads the exact evidence file.

Teams that need custom setup can instead use the repository's composite action.

## Verification and evidence tiers

```bash
dspy-security-bench proofrun verify proofrun.json --offline
dspy-security-bench proofrun verify proofrun.json --require-trusted-builder
```

Offline verification recomputes all raw-trial statistics and hashes. Online
verification additionally validates the attestation, repository, source commit,
ref, runner environment, and workflow invocation. Self-hosted runners are
rejected unless a reviewer explicitly opts in.

The public evidence ladder distinguishes:

- self-attested bundles;
- caller-workflow GitHub attestations;
- the centrally controlled trusted builder; and
- content-addressed maintainer reproductions.

The dashboard also corrects an older presentation bug: capability now comes
from each model's committed no-attack evaluation, rather than displaying
utility-under-attack beneath a “benign” label.

## Honest limits

Provenance proves where exact evidence bytes came from. It does not make a
remote model API independently observable, guarantee that evaluated source is
benign, generalize beyond the five frozen synthetic scenarios, or establish
safety or regulatory compliance. The UI and verifier preserve those boundaries
instead of presenting a generic “verified” badge.

See [`docs/proofrun.md`](../proofrun.md) for the integration guide and threat
model.
